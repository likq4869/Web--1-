## 第 0 章 本次问题的根因诊断

在写新流程之前，先把当前实现的**结构性缺陷**说清楚。问题不是「文案不好」，而是**流程模型本身错了**。

### 0.1 缺陷清单（对应你提的 10 条）

| # | 你的反馈 | 根因 | 层级 |
|---|---|---|---|
| **D1** | 「我不需要里面出现模拟数据」 | `LoginSheet.vue` 的 `phoneInput` 手动输入框 + `onMockBindPhone` 直接在**生产代码路径**里；`Mock` 是后端联调态，不该出现在用户界面 | 代码 + 安全 |
| **D2** | 「绑定步骤有非常大的问题」 | 把 **wx.login 身份识别** 和 **getPhoneNumber 取号** 强行拆成两个串行步骤，违反微信「授权后置」原则；真实产品应先用静默登录拿到身份，只在**真实业务节点**要号 | 流程模型 |
| **D3** | 「未能获取微信登录凭证」不该内嵌在弹窗 | 错误信息以**静态文本**渲染在弹窗卡片里，破坏布局、占据视线、且需要用户二次阅读 | 反馈层 |
| **D4** | 「benefit-list 要去除」 | `benefit-list`（免记密码/记录仅本人可见/证据 90 天删除）是营销文案，与「每页只讲一个重点」冲突，也违反 `design.md` §13.4 | 视觉 |
| **D5** | 「协议行太长要一行」 | `agreement-text` 三个短句用 `·` 串联，必然溢出 | 视觉 |
| **D6** | 「tabBar 字体图标太丑，不是微信官方的吧？」 | 图标 PNG 仅 **81×81 / ~250–311 字节**——这个体积意味着图形几乎没画；且 `pages.json` 未设 `fontSize`，用默认 10px 显得又小又挤 | 资源 + 配置 |
| **D7** | 「微信不会自动填入号码·点下方按钮授权」不要 | 这是**对用户的科普**，正确做法是把信息塞进按钮文案，说明放按钮下方一行 | 文案 |
| **D8** | 「或手动输入」及以下都不要 | 同 D1；且「或手动输入」出现在**主路径**上会让用户以为需要手填 | 流程模型 |
| **D9** | 「插件头像获取失败，已继续登录」有大问题 | 这是**技术故障泄漏**到用户界面；正确做法是静默降级（用默认头像进流程） | 反馈层 |
| **D10** | 「点绑定手机后跳转登录页，到第三步了」 | `LoginSheet` 绑定成功 → `onLoginSuccess` → `has_profile` 为 false → `navigateTo('/pages/auth/auth')`，而 auth 页 `onMounted` 又重新路由判定，**导致步骤错乱**（用户明明刚绑完号，却被丢到「学籍」步） | 状态机 |
| **D11** | 「组件不要出现字符溢出」 | `.err-box` / `.agreement-text` / `.benefit-text` 缺 `min-width: 0` + 溢出保护；`.masked-num` 字号 28px 在 320px 宽屏会溢出 | 布局 |
| **D12** | （用户未察觉，但**当前编译不过**） | `App.vue` 第 6 行 `import { silentLogin } from "./utils/auth"`，但 `utils/auth.ts` **从未实现 `silentLogin`**（全仓库搜索仅命中 `App.vue` 这一处 import）。这是一个**未提交改动引入的构建期断裂**——`silentLogin` 已被调用但未导出 | 代码（阻断） |

### 0.2 三个致命设计错误的本质

**① 把「技术步骤」暴露给用户。**

现在的 4 步（登录 → 手机 → 学籍 → 同意）是**后端接口的镜像**，不是**用户心智模型**。用户不关心「手机号绑定」是一个独立步骤，他只关心「登录成功，能用」。

**② 把「登录失败」当作「登录界面的一部分」。**

错误应该是**分层**的：轻量信号走瞬时提示层，表单校验走原位字段层，阻断性问题走模态层。混成一个 `.err-box` 方块塞在卡片里，等于把瞬时信号当成了需要用户阅读的**内容**。

> ⚠️ **v2.0 对 v1.0 的修正**：v1.0 主张「所有错误都走顶部 Toast」。这**违反微信官方设计指南**：
> > 「特别注意该形式**不适用于错误提示**，因为错误提示需明确告知用户，因而不适合使用一闪而过的弹出式提示。」
> > —— [微信小程序设计指南 §2.2 页面全局操作结果](https://developers.weixin.qq.com/miniprogram/design/)
>
> 正确解法是**双层反馈模型**（详见第 8 章）：Toast 只承载瞬时信号，表单错误仍需原位可见。

**③ 主路径上存在调试通道。**

Mock 手输手机号这条路一旦上线，就是**绕过微信鉴权**的后门——任何人拿到自己的 access_token，就能把任意 11 位手机号绑到自己的账号上，从而**冒用他人手机号**（进而绑定他人学号）。这不只是体验问题，是**安全问题**（详见 §11.2）。

## 第 1 章 业界共识：三种身份能力的边界

### 1.1 三种模式对照

| 模式 | API | 用户感知 | 拿到什么 | 何时用 | 成本 | 合规风险 |
|---|---|---|---|---|---|---|
| **静默登录** | `wx.login()` → `code2Session` | **零感知** | `openid` / `unionid` / `session_key` | App 启动即执行，建立本地身份 | 免费 | 最低 |
| **资料授权** | 安全注册插件 `<login>` 或 `chooseAvatar` + `input[type=nickname]` | 一次弹窗授权 | `avatarUrl` / `nickName`（仅展示） | 需要在页面展示头像昵称时 | 免费 | 低 |
| **手机号快速验证** | `<button open-type="getPhoneNumber">` → `phonenumber.getPhoneNumber` | 一次系统弹窗 | 真实手机号（平台已验证） | **真实业务节点**：绑定学号、订阅消息、申诉联系 | **0.03 元/次**（成功才扣费） | 中（需隐私指引声明用途） |

> **核心判断依据**（联网核验）：
> > 「`wx.login()` 用于识别小程序用户并建立业务登录态，`getPhoneNumber` 用于获取手机号。**后端应把手机号绑定到已经登录的业务用户**，不能只凭手机号 `code` 创建不受控的账号绑定关系。」
> > —— [手机号授权关联实践指南](https://www.alexsummer.icu/%E5%BE%AE%E4%BF%A1%E7%94%9F%E6%80%81/%E5%BE%AE%E4%BF%A1%E4%B8%8E%E4%BC%81%E4%B8%9A%E5%BE%AE%E4%BF%A1%E8%8E%B7%E5%8F%96%E6%89%8B%E6%9C%BA%E5%8F%B7%E5%AE%9E%E7%8E%B0%E6%8C%87%E5%8D%97/)
>
> > 「不要把静默登录、用户信息授权全部堆在同一个登录页上一股脑执行，那样用户会被连续几个弹窗吓跑。」
> > —— [codechina《微信小程序登录页面全解析》](https://codechina.net/article/weixin_29189363/402433)

### 1.2 官方硬性规定（提审红线）

> 微信开放社区《小程序帐号登录规范要求与修改指引》原文要点：

- **「用户未触发需使用权限或用户个人信息的相关功能或服务时，不得提前向用户申请权限或收集用户个人信息。」**
- 「授权个人信息功能**后置**，给予用户充分了解、体验功能服务后，再由用户主动点击进一步功能触发登录授权。」
- 「体验范围开放」类小程序：首页打开即要求授权登录 → **判违规**。
- 提供了拒绝按钮但点击「取消/拒绝」无响应仍强制登录 → **判违规**。
- 手机号快速验证组件：**仅对非个人主体且已完成认证的小程序开放**。
- 手机号快速验证组件**启动页不放**（属于「囤数据」，驳回概率最高）。
- `getPhoneNumber` 返回的 `code` 与 `wx.login` 返回的 `code` **不可混用**；`phone_code` 有效期 5 分钟、**只能用一次**。
- `code` 必须在**服务端**换取手机号（前端绝不持有 AppSecret / 解密密钥）。

### 1.3 隐私协议同步机制（联网核验新增，v2.0 补充）

自基础库 **2.32.3** 起，隐私同意按钮支持与手机号快速验证组件**耦合**：

```html
<button
  id="agree-btn"
  open-type="getPhoneNumber|agreePrivacyAuthorization"
  bindgetphonenumber="handleGetPhoneNumber"
  bindagreeprivacyauthorization="handleAgreePrivacyAuthorization"
>
  同意协议并授权手机号
</button>
```

- 「**仅有在指引中声明所处理的用户信息，才可以调用平台提供的对应接口或组件。若未声明，对应接口或组件将直接禁用。**」
- `wx.getPrivacySetting` → `res.needAuthorization` 判断是否需要先弹隐私协议。
- `wx.onNeedPrivacyAuthorization` 可被动监听隐私接口触发的授权事件，配合 `resolve({ buttonId, event })` 放行或阻断。
- 「对于 `button` 组件，由于 `getPhoneNumber` 的特殊性，如果用户未同意隐私协议，则聚焦时不会触发 `onNeedPrivacyAuthorization` 事件，而是降级为 `fail`。」

> **对本项目的含义**：取号按钮**必须**先完成隐私协议同步，否则 `getPhoneNumber` 会静默降级为 `fail`（用户什么都不知道，只看到"没反应"）。这是 D3/D7 类问题的一个隐藏根因。

### 1.4 成本与配额（必须纳入设计）

- 每次 `getPhoneNumber` **成功**扣 0.03 元；每个小程序 1000 次体验额度（开发/体验/正式**共用**）。
- 免费主体：政府、非营利组织、事业单位（政务民生）、**公立医疗机构 / 学历教育（学校）**。
  → 本项目为**校园**类，若主体为学校可申请免费；否则需在付费管理中购买资源包。
- **因此：「能不用取号就不取号」。** 只有真正需要号码绑定学号时才取，且**取一次就用一次**，不做重复取号。
- 扣费节点是 `bindgetphonenumber` 的 success 回调 → 拿到 `code` 后**必须立即提交后端**，中途失败要记账。

## 第 2 章 最优流程总览（状态机）

### 2.1 分层架构（关键认知）

> **最重要的一个决策：把「身份识别」与「资料采集」彻底解耦成两条独立的通道。**

```
┌───────────────────────────────────────────────────────────────────────┐
│ 通道 A：身份通道（静默 · 零感知 · App 启动即跑）                        │
│                                                                       │
│   wx.login() ──code──▶ 后端 code2Session ──openid──▶ 签发本系统 token  │
│                                                                       │
│   产出：用户已登录（本地态）。**不弹任何窗、不问用户任何问题。**         │
│   价值：首屏流失率最低，随时可发请求。                                  │
└───────────────────────────────────────────────────────────────────────┘
                                    │
                    用户触发「需要身份」的业务动作
                    （看积分 / 看记录 / 绑定学号 / 申诉）
                                    │
                                    ▼
┌───────────────────────────────────────────────────────────────────────┐
│ 通道 B：资料通道（显式 · 渐进式 · 一次一件）                            │
│                                                                       │
│   B1 头像昵称 ──chooseAvatar + nickname──▶ 仅展示用（可选，可跳过）     │
│   B2 手机号   ──getPhoneNumber──▶ 身份唯一锚点（取一次，绑学号时）      │
│   B3 学籍     ──picker 级联 + 学号 + 姓名──▶ 业务必需                 │
│   B4 知情同意 ──复选框──▶ 合规收口                                    │
│                                                                       │
│   规则：每个字段在**真实需要它的节点**才要，绝不在登录时打包索取。       │
└───────────────────────────────────────────────────────────────────────┘
```

### 2.3 与当前实现的差异

| 维度 | 当前 | 目标 |
|---|---|---|
| wx.login 时机 | 用户点「微信一键登录」按钮后 | **App 启动静默执行**（`App.vue` / `onLaunch`，已有雏形） |
| 登录页角色 | 承载全部 4 步 | 只承载**资料补全**（学籍 / 同意），wx+phone 由**弹窗 + 原生组件**承接 |
| 手机号获取 | 「绑定手机号」独立卡片页 | **在需要绑学号的那一刻**才取号（业务节点） |
| 插件失败 | 弹「插件头像获取失败，已继续登录」 | **静默降级**，用默认头像继续；不向用户暴露技术故障 |
| 手动输手机号 | 存在（主路径） | **移出生产代码**，仅保留在开发联调开关内（`__DEV__` 且后端 Mock 态） |
| 错误呈现 | 内嵌 `.err-box` 静态文本 | **双层反馈模型**（顶部轻提示 + 字段级原位错误，见第 8 章） |
| 步骤跳转 | `navigateTo` 后 auth 页重新路由判定 | **单一状态源**（store 持有 `authStage`），页面只渲染不改状态 |

## 第 3 章 阶段一：无感身份建立（wx.login 静默登录）

### 3.1 时序

```

 │                │ wx.login()           │                      │
 │                │─────────────────────▶│                      │
 │                │◀──── code (5min,1次) │                      │
 │                │                      │                      │
 │                │ POST /auth/wechat-login {code}              │
 │                │─────────────────────▶│                      │
 │                │                      │ GET jscode2session   │
 │                │                      │─────────────────────▶│
 │                │                      │◀─ openid/unionid/   │
 │                │                      │   session_key        │
 │                │                      │                      │
 │                │                      │ upsert by openid     │
 │                │                      │ 签发 access/refresh  │
 │                │◀─ {access_token, refresh_token, user}        │
 │                │                      │                      │
 │                │ 写 storage（静默）     │                      │
 │ 看到首页内容    │                      │                      │
 │（无任何弹窗）   │                      │                      │
```

### 3.2 实现要点

1. **在 `App.vue` 的 `onLaunch` 触发**，而不是在登录页。
   ```ts
   // miniprogram/src/App.vue（当前已有，需补单例锁）
   onLaunch(() => {
     // 静默建立身份：失败不打扰用户，游客态照样可用
     void silentLogin().catch(() => {});
   });
   ```

2. **`code` 一次性、5 分钟有效**：拿到就立刻用，失败可重试（重新 `wx.login` 拿新 code）。

3. **静默登录失败不弹窗**，只置 `loggedIn = false`，走游客态。

4. **`session_key` 只落服务端**，绝不返回前端（微信官方明确要求）。

5. **openid 不暴露前端**；前端只持本系统签发的 JWT。

6. **登录态自动续期**：`api.ts` 已有 401 → refresh → 重放一次 + 并发刷新锁，**保持不动**（属现有优秀实践）。

7. **禁止重复 wx.login**：加 `loginPromise` 单例（同一时刻只发一次）。

### 3.3 合规要点

- 静默登录属于「识别身份」，不涉及个人信息，**不需要用户同意**。
- 但小程序后台「用户隐私保护指引」仍应声明使用 `openid` 的用途。
- `wx.getPrivacySetting` / `wx.requirePrivacyAuthorize` **只在用户主动触发登录时**才检查，不要一进小程序就弹。

> ⚠️ **注意一个真实存在的坑**（联网核验发现，业界普遍反馈）：
> 「早期版本在小程序启动时就静默 `wx.login` 并请求后端登录接口，结果被平台提示**隐私协议未同意就收集用户信息**，后来改成了用户点击登录按钮时才触发 `wx.login`，并前置弹出隐私弹窗。」
> —— [codechina《微信小程序登录页面全解析》](https://codechina.net/article/weixin_29189363/402433)
>
> **本项目的处理**：静默登录**只调 `wx.login` 换 openid**，不收集任何个人信息（openid 是账号标识不是个人信息）。但仍需在隐私指引中声明 `openid` 用途。若审核时被驳回，降级方案见 §10.1（静默登录失败降级为游客态，即「不静默」）。

## 第 4 章 阶段二：头像昵称获取（安全注册插件 / chooseAvatar）

### 4.1 两条可选路径

| 路径 | 组件 | 优点 | 缺点 | 推荐 |
|---|---|---|---|---|
| **A. 安全注册插件** | `plugin://loginplugin/login` | 微信原生弹窗，**一次授权同时拿到头像+昵称**，无需用户填表 | 需后台申请插件 + 类目「工具->办公」；**极少机型会 fail** | ✅ 首选（有插件时） |
| **B. chooseAvatar + nickname** | `<button open-type="chooseAvatar">` + `<input type="nickname">` | 无需插件申请，兼容性最好 | 昵称需要用户点一下输入框选微信昵称 | ✅ 兜底 |

### 4.2 官方插件用法（已验证的调用形态）

**声明**（`manifest.json → mp-weixin.plugins`）：
```json
"plugins": {
  "loginplugin": { "version": "latest", "provider": "wxc7b7f914565de923" }
}
```

**页面注册**（`pages.json → style["mp-weixin"].usingComponents`）：
```json
"mp-weixin": { "usingComponents": { "login": "plugin://loginplugin/login" } }
```

> ⚠️ **关键坑（当前代码已踩过并已注释）**：`usingComponents` 注册**只对页面模板生效**。
> 把 `<login>` 写在子组件（`LoginSheet.vue`）里 → 编译出的 `LoginSheet.json` 没有 plugin 声明 → **点了没反应**。
> **所以 `<login>` 必须渲染在页面根部**，由子组件通过事件请求页面拉起。

**组件用法**：
```html
<!-- 页面根部 -->
<login
  v-if="pluginVisible"
  class="login-modal"
  :modal="pluginModal"
  @success="onPluginSuccess"
  @fail="onPluginFail"
  @cancel="onPluginCancel"
/>
```
```ts
// modal 只支持 title / content；按钮文案与样式由插件固定，不可自定义
const pluginModal = {
  title: '完善你的资料',
  content: '用于展示头像与昵称，仅本人可见',
};
```

**回调体解析**（两个包法都要兜）：
```ts
function pickPluginRes(e: unknown): { avatarUrl?: string; nickName?: string } {
  const obj = (e ?? {}) as {
    target?: { res?: { avatarUrl?: string; nickName?: string } };
    detail?: { res?: { avatarUrl?: string; nickName?: string } } & { avatarUrl?: string; nickName?: string };
  };
  if (obj.target?.res) return obj.target.res;
  if (obj.detail?.res) return obj.detail.res;
  if (obj.detail) return obj.detail;
  return {};
}
```

### 4.3 插件失败 / 取消的正确处理（修正 D9）

当前实现的问题：`autoTip.value = '插件头像获取失败，已继续登录'` —— 把技术故障推给用户。

**企业级处理原则**：

| 事件 | 含义 | 正确处理 | 是否提示用户 |
|---|---|---|---|
| `success` | 授权成功 | 缓存 `avatarUrl` / `nickName`，继续流程 | ❌ 不提示 |
| `fail` | 极少数机型插件异常 | **静默降级**：用默认头像 + 空昵称，**继续流程** | ❌ **不提示**（技术上不可解释，用户无法行动） |
| `cancel` | 用户主动取消 | 静默返回登录页，保持未登录 | ❌ 不提示（用户是主动取消的，提示是噪音） |
| **超时无回调**（3s） | 后台没加插件 / 类目不对 / 未重新编译 | 自动走自建链路（`wx.login` + `chooseAvatar`） | ❌ 不提示 |

> **「fail 也当成功处理」是官方经验帖的明确建议**：因为业务要求登录才能用，
> 若 fail 就阻断，这部分用户会永久无法登录。头像昵称只是**展示用装饰**，失败不应阻断主流程。

**唯一应该提示的情况**：整条链路都失败（`wx.login` 也拿不到 code），且这是**用户可行动**的
（如网络异常、需重试）。此时用**顶部轻提示**（见第 8 章），文案：「登录未完成，请重试」。

### 4.4 头像昵称的使用边界（对齐 AGENTS.md 原则 6）

- 插件/chooseAvatar **只取必要字段**：`avatarUrl` / `nickName`，**仅用于页面展示预填**。
- `openid` / `phone_code` **仍走后端三件套**，不从插件拿。
- **人脸 / 身份证影像不落库、不透传后端。**
- 头像 URL 落库时**截断长度**（当前后端 `avatar[:512]` 已做）。
- 学生端文案不得出现「处罚/违规/记过」等字眼。

## 第 5 章 阶段三：手机号绑定（getPhoneNumber 快速验证组件）

### 5.1 什么时候取号（业务节点判定）

> **唯一取号时机：用户提交学籍（学号 + 姓名）时，需要把学号锚定到一个真实身份上。**

| 场景 | 是否取号 | 理由 |
|---|---|---|
| 打开首页、浏览工具 | ❌ | 游客态可浏览（官方要求「体验范围开放」） |
| 拍照自查（`index` 页） | ❌ | 自查是工具功能，与身份无关 |
| 查看自己的积分 / 记录 | ❌→✅ | 需要识别「你是谁」→ **此时取号** |
| **提交学号 + 姓名** | ✅ | 学号必须绑定真实号码，防止冒用他人学号 |
| 申诉 | ✅（若尚未绑定） | 申诉要能联系到本人 |
| 订阅消息 | ✅ | 订阅消息本身就是手机号场景 |

**关键设计：合并取号与学籍提交。**
不要先绑号再填学籍（两步），而是：**填完学籍 → 点「提交」→ 弹微信取号授权 → 拿到号 → 一次提交（学号+号码）**。
用户感知是「一次点击完成绑定」，实际是两次 API 调用。

### 5.2 前端实现（修正 D7 / D8）

**不要**这样写（当前实现的问题）：
```html
<!-- ❌ 错误：科普文案 + 手动输入兜底 -->
<text class="body-text">微信不会自动填入号码，需点下方按钮授权；仅用于找回与通知，不做他用。</text>
<button open-type="getPhoneNumber">微信一键绑定</button>
<view class="divider"><text>或手动输入</text></divider>
<input v-model="phoneInput" placeholder="11 位大陆号码" />
<button @click="onMockBindPhone">使用该号码绑定</button>
```

**应该**这样写：
```html
<!-- ✅ 正确：按钮即说明，下方一行补充用途 -->
<button
  class="primary-btn"
  open-type="getPhoneNumber"
  :disabled="busy"
  @getphonenumber="onGetPhoneNumber"
>
  <text>{{ busy ? '绑定中…' : '本机号码一键绑定' }}</text>
</button>
<text class="bind-note">仅用于确认你是本人，配合学号关联你的安全记录</text>
```

**按钮文案规范**（业界通行）：
- ✅ 「本机号码一键绑定」「微信手机号一键登录」「用本机号码继续」
- ❌ 「微信不会自动填入号码」（科普，应放按钮下方）
- ❌ 「微信一键绑定」（太笼统，用户不知道会发生什么）

> **微信官方对「不要科普」的佐证**：《小程序设计指南》§1.1「重点突出」——「尽量避免页面上出现其他与用户的决策和操作无关的干扰因素」。对用户解释微信的工作原理属于干扰信息。

### 5.3 事件处理（完整错误处理）

```ts
interface PhoneEvent {
  detail?: { code?: string; errMsg?: string; errno?: number };
}

async function onGetPhoneNumber(e: PhoneEvent): Promise<void> {
  if (busy.value) return;                 // 防连点重复计费
  const errno = e.detail?.errno;
  const errMsg = e.detail?.errMsg ?? '';

  // ① 额度不足（1400001）：平台半屏提示已给出，这里不重复提示
  if (errno === 1400001) {
    toastWarning('服务额度已用尽，请稍后再试');
    return;
  }
  // ② 用户拒绝 / 取消：区分两种，不重复弹窗，不当失败
  if (errMsg.includes('deny') || errMsg.includes('cancel')) {
    toastInfo('已跳过手机号绑定，可稍后在「我的」中补充');
    return;   // ← 关键：不置错误态，不清空表单，用户可继续
  }
  // ③ 无 code：可重试
  const code = e.detail?.code ?? '';
  if (!code) {
    toastError('未获得手机号授权，请重试');
    return;
  }
  // ④ 正常路径：立即提交后端（code 5 分钟有效、只能用一次）
  busy.value = true;
  try {
    await store.bindPhone(code);          // 后端换号 + 落库 + 签发
    toastSuccess('绑定成功');
    await advanceStage();                 // 只改状态，不做跳转（取号弹窗期禁止跳转）
  } catch (err) {
    toastError(err instanceof Error ? err.message : '手机号绑定失败，请重试');
  } finally {
    busy.value = false;
  }
}
```

### 5.4 强制约束（踩过坑必须写死）

1. **取号弹窗期间禁止任何跳转**。
   官方《手机号计费误差问题排查指南》第 3 条明确：在手机号授权弹窗时调用
   `wx.reLaunch` / `wx.navigateTo` / `wx.redirectTo` / `wx.navigateBack`，会导致**收不到 `bindgetphonenumber` 回调**。
   → **禁止在 `onGetPhoneNumber` 里做任何页面跳转**，只改状态。

2. **拿到 code 后立即提交**（5 分钟有效、一次有效、且成功即计费）。

3. **按钮立即隐藏或置 `disabled`**（防止重复点击重复计费）。

4. **`phone_code` 与 `wx.login` 的 `code` 不可混用**，后端要分开两个字段。

5. **服务端解密**：`phonenumber.getPhoneNumber` 必须在后端调用，AppSecret 只存服务端。

6. **入库脱敏**：审计日志只留 `***1234` 掩码（后端已实现）。

7. **可用 `openid` 校验绑定关系**（官方文档明确支持，v2.0 新增）：
   > 请求体参数 `openid`（选填）：「用户openid，填入后会校验openid和code的绑定关系，并在不匹配时报错」
   > —— [获取手机号（服务端）](https://developers.weixin.qq.com/miniprogram/dev/server/API/user-info/phone-number/api_getphonenumber.html)

   → **强烈建议后端补上这个参数**，防止 `phone_code` 被跨用户盗用。

8. **隐私协议必须先同步**（见 §1.3）：否则 `getPhoneNumber` 会降级为 `fail`，用户看不到原因。

### 5.5 计费保护（企业级必备）

| 保护 | 实现 |
|---|---|
| 不重复取号 | `has_phone` 为 true 时不再渲染取号按钮 |
| 防连点 | 按钮 `:disabled="busy"`，回调内 `if (busy.value) return` |
| 失败记账 | 后端记录 `getPhoneNumber` 成功但换号失败的次数，用于对账 |
| 额度预检 | 平台在**用户点击时**查额度，额度不足返回 `errno=1400001`；可用 `phone-number-no-quota-toast="false"` 关闭平台半屏提示改用自定义文案 |

## 第 8 章 反馈层规范（双层模型）★核心修正

> 这是你提的第 3 点，也是本次改动中**最有价值的一次范式升级**。
> **v2.0 相对 v1.0 的关键修正**：不再主张「所有错误都走 Toast」。

### 8.1 为什么不能只有一种反馈形式

微信官方《小程序设计指南》§2.2 明确把反馈分成三级：

| 层级 | 官方定义 | 适用 | 禁止 |
|---|---|---|---|
| **Toast / 弹出式提示** | 「适用于轻量级的成功提示，1.5秒后自动消失，并不打断流程」「适用于需要轻量化地用文字解释当前状态或提醒**不严重的错误**」 | 成功、已跳过、网络瞬时抖动 | ❌「**不适用于错误提示**，因为错误提示需明确告知用户」 |
| **公告报错** | 「表单报错，在表单顶部告知错误原因，并标识出错误字段提示用户修改」 | 表单字段校验失败 | — |
| **模态报错** | 阻断并给出下一步操作指引 | 阻断性错误（账号被冻结、学号冲突） | — |

> **结论**：你要的「顶部滑入滑出」效果业界叫 **Snackbar / 顶部轻提示**，它是**正确的**反馈形式，
> 但**只该承载瞬时信号**。真正需要用户"看清并行动"的错误，必须有**常驻的、可定位的**呈现。

### 8.2 双层反馈模型（本项目落地标准）

```
┌─────────────────────────────────────────────────────────────────┐
│ 第 1 层：顶部轻提示（TopToast）—— 瞬时信号层                     │
```

### 8.7 关键实现细节

> 小程序机制**不允许动态插入 DOM**（`wx.showToast` 的替代品必须预置节点）。

1. **组件常驻 DOM**，用 `visible` / `leaving` 控制显隐，不用 `v-if` 卸载（否则退场动画跑不了）。

2. **定时器自管理**：`show()` 时 `clearTimeout` 旧定时器再起新的，避免连续调用堆叠。

3. **不可用原生 `wx.showToast`**：位置固定居中、不支持自定义颜色与左边条、时长不可控、无法做「从顶部滑入」。

5. **auth 页用原生导航栏**，`top` = 状态栏高度即可——已在 `App.vue` 的 `onShow` 中按当前路由重算，**当前实现正确**。

### 9.1 文本溢出修复（修正 D11）

小程序 `text` 组件默认 `display: inline`，**长文不换行会溢出容器**。统一规则：

| 场景 | 规则 |
|---|---|
| 单行截断 | `white-space: nowrap; overflow: hidden; text-overflow: ellipsis;` + 父级 `min-width: 0` |
| 多行限高 | `display: -webkit-box; -webkit-line-clamp: N; -webkit-box-orient: vertical; overflow: hidden;` |
| Flex 子项 | 必须加 `min-width: 0`（默认 `auto` 不收缩） |
| Grid 子项 | 必须加 `min-width: 0` 或 `overflow: hidden` |
| 数字 | 一律 `font-variant-numeric: tabular-nums`（铁律④，全局已开，组件内不得关闭） |

```scss
  white-space: nowrap;
```

### 9.3 tabBar 图标重做（修正 D6）

#### 现状诊断（实测数据）

| 图标 | 尺寸 | 体积 | 问题 |
|---|---|---|---|
| `home.png` | 81×81 | **307 B** | 极端简化的位图，线条细节全无，放大后锯齿严重 |
| `home-active.png` | 81×81 | **302 B** | 同上 |
| `scan.png` | 81×81 | **252 B** | 同上 |
| `scan-active.png` | 81×81 | **247 B** | 同上 |
| `mine.png` | 81×81 | **311 B** | 同上 |
| `mine-active.png` | 81×81 | **306 B** | 同上 |

**根因**：PNG 体积 ~250–310B（全部为 `colortype=6` RGBA + `bitdepth=8`）意味着**几乎是纯色块或极简几何**，
没有 1px 描边、没有圆角细节。一个合格的单色线性 tabBar 图标 PNG 通常 **2–6 KB**。
300B = **图标几乎没画**——这就是「太丑」的真正原因。

**另外**：`pages.json → tabBar` 未设置 `fontSize` / `iconWidth`，使用微信默认值
（`fontSize: 10px`, `iconWidth: 24px`），在小屏上「首页 / 头盔自查 / 我的」会显得**又小又挤**，
尤其「头盔自查」四个字挤在 141px 宽的格子里。

> **回答你的疑问**：「这个好像不是微信官方的底部栏吧？」
> → **tabBar 本身是微信原生的**（`pages.json` 里 `custom` 未设，即 `false`），
> 渲染由微信负责，样式统一、可点击区域精准、无兼容问题。
> **丑的是那 6 张 PNG 图标**，不是 tabBar 组件本身。所以**不要**改造成自定义 tabBar
> ——那会引入大量兼容与回归成本（须同步选中态、安全区、全入口回归），而问题只在图片。

#### 官方规范（已联网核对 2026-11-10 版官方文档）

- 图标**建议 81px × 81px**，**限制 40KB 以内**，**不支持网络图片**（必须本地文件）。
- 必须分别提供 `iconPath`（未选中）与 `selectedIconPath`（选中）。
- `color` / `selectedColor` / `backgroundColor` / `borderStyle` 均为必填。
- 标签数量 **2–5 个**（当前 3 个，合规）。
- `iconWidth` 默认 24px，`fontSize` 默认 10px，`selectedFontSize` 默认 10px。
- 设计侧规范：「图标控件尺寸是 **54×54px**，但小程序开发需要的是 **81×81px**，正好是 1.5 倍，需要注意一次给到位。」

#### 重做规范

| 项 | 标准 |
|---|---|
| 尺寸 | **81 × 81 px**（保持当前尺寸，符合官方建议） |
| 格式 | PNG-8 或 PNG-24，带 alpha（当前 colortype=6 可保持） |
| 体积 | 2–6 KB（当前 250–311B 明显不合格） |
| 风格 | **单色线性（outline）**，线宽 2px @81px（≈ 视觉 24px 时 0.6px），端点圆角 |
| 视觉重量 | 图标在 24px 显示尺寸下应清晰可辨，不糊成一团 |
| 配色 | 未选中 `#8e8e93`（与 `tabBar.color` 一致）；选中 `#2f6b4f`（与 `selectedColor` 一致） |
| 禁止 | 网络图 / SVG / iconfont / emoji（AGENTS.md §10 明确） |
| 形状 | 与 `design.md` §13.2 的工具宫格图标保持同一套几何语言 |

**图形建议**（与项目语义一致）：
- **首页** → 房屋轮廓（屋顶折线 + 墙体），线宽 2px
- **头盔自查** → 头盔侧影轮廓（半圆盔体 + 帽檐短线），比「扫描框」更贴题
- **我的** → 人像轮廓（头圆 + 肩弧线），比「齿轮」更直观

### 11.2 必改项（后端）★安全漏洞

#### ① `bind-phone` 的 `phone` 直传必须生产禁用（**真实漏洞**）

当前 `WechatClient.resolve_phone` 的实际逻辑（`helmet-guard/app/services/auth/wechat_client.py:165-188`）：

```python
def resolve_phone(self, phone_code: str | None, phone: str | None) -> str:
    if phone_code and phone_code.strip() and not self.is_mock:
        return self._phone_by_code(phone_code.strip())
    # Mock 模式：直传 phone 即为最终号码
    if phone and phone.strip():          # ← ⚠️ 这里没有 `not self.is_mock` 守卫！
        return phone.strip()
    ...
```

**问题**：`not self.is_mock` 守卫**只保护了 phone_code 分支**，`phone` 直传分支**在生产模式下同样会命中**。
结果：**任何人拿到自己的 access_token，就能把任意 11 位手机号绑到自己的账号上**，
从而冒用他人手机号（进而绑定他人学号、冒领积分/安全记录）。

**修复**：
```python
def resolve_phone(self, phone_code: str | None, phone: str | None) -> str:
    """解析手机号。

    生产模式**只接受**微信 phone_code；直传 phone 仅在 Mock 联调态放行。
    """
    if phone_code and phone_code.strip():
        if self.is_mock:
            raise ExternalServiceError(
                "Mock 模式无法通过 code 解析手机号，请在开发联调开关内直传 phone"
            )
        return self._phone_by_code(phone_code.strip())
    if phone and phone.strip():
        if not self.is_mock:
            raise PermissionDeniedError("生产环境不接受直传手机号，请使用微信手机号授权")
        return phone.strip()
    raise ExternalServiceError("缺少手机号凭证")
```

**并在 `settings` 增加显式开关**（默认关，联调时开）：
```python
allow_direct_phone_bind: bool = False   # 仅开发联调，生产必须 False
```
由 `AuthService.bind_phone` 强制校验：**生产环境（`settings.environment != "dev"`）直传一律拒绝**。

#### ② `_phone_by_code` 应传 `openid` 校验绑定关系

官方接口明确支持 `openid` 选填参数：「填入后会校验openid和code的绑定关系，并在不匹配时报错」。

```python
def _phone_by_code(self, phone_code: str, openid: str | None = None) -> str:
    ...
    payload: dict[str, object] = {"code": phone_code}
    if openid:
        payload["openid"] = openid   # 微信会校验 code 与 openid 的绑定关系
```
`AuthService.bind_phone` 需把当前用户的 `openid` 传进去，防 `phone_code` 跨用户盗用。

#### ③ `access_token` 必须缓存（不要每次请求都取）

联网核验：「后端必须获取并**缓存**小程序 `access_token`，不要在每次手机号请求时重新获取。
多实例部署时应使用 Redis 和分布式锁统一刷新。」→ 当前 `_access_token()` 实现需确认是否已缓存。

#### ④ 新增「一次提交」接口（可选，推荐）

把「取号 + 绑学号」合并为一个原子操作，避免中间态：
```jsonc

  "phone_code": "xxx",          // 来自 getPhoneNumber

```
→ 响应 `{user, student, has_phone, has_profile}`。
后端在一个事务内：换号 → 落号 → upsert 学籍 → 审计。
**好处**：学号与手机号强绑定，杜绝「先占学号后补号」的中间态被滥用。

#### ⑤ 服务端安全清单（联网核验补充）

- Secret 只存服务端环境变量或密钥管理服务。
- `access_token` 用 Redis 等集中式缓存。

### A.2 静默登录（需补单例锁）

`miniprogram/src/utils/auth.ts`
```ts
let loginPromise: Promise<MiniUser | null> | null = null;

/**
 * 静默登录：wx.login → code2Session → 签发本系统令牌。
 * 不弹任何授权窗；失败不打扰用户（返回 null，游客态可用）。
 */
export function silentLogin(): Promise<MiniUser | null> {
  if (loginPromise) return loginPromise;
  loginPromise = (async () => {
    try {
      const code = await wxLoginCode();
      if (!code) return null;
      return await loginWithWechat(code);
    } catch (_) {
      return null;
    } finally {
      // 允许下一次重新尝试（登录态失效时需要）
      setTimeout(() => { loginPromise = null; }, 0);
    }
  })();
  return loginPromise;
}
```

### A.3 取号（正确处理拒绝/失败/隐私降级）

```ts
async function onGetPhoneNumber(e: PhoneEvent): Promise<void> {
  if (busy.value) return;                 // 防连点重复计费
  const errno = e.detail?.errno;
  const errMsg = e.detail?.errMsg ?? '';

  if (errno === 1400001) {
    toastWarning('服务额度已用尽，请稍后再试');
    return;
  }
  if (errMsg.includes('deny') || errMsg.includes('cancel')) {
    // 用户拒绝是权利，不是错误：不置错误态、不清空表单
    toastInfo('已跳过手机号绑定，可稍后在「我的」中补充');
    return;
  }
  const code = e.detail?.code ?? '';
  if (!code) {
    toastError('未获得手机号授权，请重试');
    return;
  }

  busy.value = true;
  try {
    await store.bindPhone(code);
    toastSuccess('手机号绑定成功');
    await advanceStage();                 // 只改状态，不做跳转（取号弹窗期禁止跳转）
  } catch (err) {
    toastError(err instanceof Error ? err.message : '手机号绑定失败，请重试');
  } finally {
    busy.value = false;
  }
}
```
