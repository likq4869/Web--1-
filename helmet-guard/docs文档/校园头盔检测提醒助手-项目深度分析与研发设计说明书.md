## 1. 项目现状深度剖析

### 1.1 当前代码资产盘点

经过对 `helmet-guard/` 与 `miniprogram/` 全量代码的审阅，目前项目已具备一个**结构清晰、工程规范度较高**的检测原型：

| 模块 | 文件 | 职责 | 成熟度评价 |
|---|---|---|---|
| 后端 API | `app/main.py` | FastAPI 入口、健康检查、统计、事件查询、复核、自查上传 | ★★★★☆ 健壮（双层上传限流、并发名额、幂等复核） |
| 数据访问 | `app/db.py` / `app/store.py` | SQLite 表结构、参数化 SQL、短事务 | ★★★☆☆ 仅 6 张表，业务表缺失严重 |
| 采集进程 | `app/detect.py` | 摄像头/视频/图片 → YOLOv8 track → 通行判定 → 入库 | ★★★☆☆ 核心链路跑通，缺身份与惩罚 |
| 判定算法 | `app/tracks.py` | 跨帧投票、头部归属、越线去重 | ★★★★☆ 纯函数设计优秀，可测 |
| 权重守卫 | `app/vision.py` | 拒绝 COCO 通用权重、ROI 几何 | ★★★★☆ 安全意识到位 |
| 提醒队列 | `app/alerts.py` | 提醒入队、限频、静默、WAV 播放 | ★★☆☆☆ 仅本地单机播放 |
| 自查模块 | `app/selfcheck.py` | 手机拍照自查、三态判定、模型 pin | ★★★★☆ 质量最高模块 |
| 配置 | `app/config.py` | 点位 ROI、计数线、提醒区 | ★☆☆☆☆ **硬编码单点位，是最大瓶颈** |
| 小程序 | `miniprogram/src/` | 拍照 → 上传 → 三态结果 → 识别依据可视化 | ★★★★☆ UI/UX 优秀，状态机严谨 |

### 1.2 已验证的核心能力（可直接复用的资产）

1. **模型可用性守卫机制**（`vision.py:is_helmet_weights` / `is_selfcheck_weights`）
   - 强制要求权重同时包含 `Cyclists` / `helmet` / `no helmet` 三类，否则拒绝启动。
   - 这是极佳的工程实践，**必须保留**并在后续所有模型切换中沿用。

2. **跨帧一致性判定 + 保守三态**（`tracks.py:decide_pass` / `selfcheck.py:decide_status`）
   - 采用 `helmeted / bare / unknown` 三态而非二态，**"unknown" 是本项目最重要的设计资产**。
   - 在证据不足（多人、多头部候选、置信度低、头部无法归属）时一律返回 unknown 而非误判。
   - 这直接对应了"AI 决策 + 人工审批"闭环的可行性基础。

3. **AI 决策可解释性**（`selfcheck.py` 返回 `reason_code` + `boxes` + `model_version`）
   - 小程序前端完整展示了"识别依据"（置信度、归一化框坐标、模型版本、推理耗时）。
   - 这是**申诉机制的基础**，人工复核与学生申诉都需要它。

4. **心跳上报机制**（`app/detect.py` → `heartbeats` 表 → `/health`）
   - 采集进程主动上报 `model_loaded / had_first_frame / frames / stage`，API 不猜测文件状态。
   - 天然适合扩展为**多设备在线状态监控**。

5. **幂等与并发安全的复核流程**（`store.py:apply_review`）
   - `BEGIN IMMEDIATE` + 条件 UPDATE `WHERE status='pending'`，并发复核只有一个成功。
   - 这套模式可直接扩展到**决策审批的并发场景**。

### 1.3 现状的五个致命缺口

| # | 缺口 | 影响 | 严重度 |
|---|---|---|---|
| 1 | **无身份识别层** | 知道"有人没戴盔"，但不知道"是谁"，无法扣分/通报 | 🔴 阻断级 |
| 2 | **无积分/惩罚/申诉域** | `passes/events/reviews/alerts` 4 张表都是"检测日志"，不是"管理闭环" | 🔴 阻断级 |
| 3 | **无 AI 决策引擎** | 现状是"模型判定 → 人工二选一"，不是"AI 自动决策 + 人工审批" | 🔴 阻断级 |
| 4 | **单点位硬编码** | `config.py` 里 ROI/计数线写死，无法多校门部署 | 🟠 高 |
| 5 | **无 Vue3 管理后台** | 用户提到的 Vue3 后台在仓库中**不存在**（`miniprogram` 是 UniApp 小程序） | 🟠 高 |

> ⚠️ **重要发现**：项目中不存在 Vue3 管理后台代码。`miniprogram/` 是 UniApp 编译到微信小程序的**学生端**。需要从零新建 `admin-web/`。

### 1.4 模型质量现状（关键风险）

训练结果（`runs/detect/helmet-v2-baseline/results.csv`，20 epoch，CPU 训练）：

```
epoch 20: precision=0.696, recall=0.425, mAP50=0.457, mAP50-95=0.253
```

| 指标 | 当前值 | 生产要求 | 差距 |
|---|---|---|---|
| Precision | 0.696 | ≥ 0.90 | -0.20 |
| Recall | 0.425 | ≥ 0.85 | -0.42 |
| mAP50 | 0.457 | ≥ 0.85 | -0.39 |

**这意味着：当前模型漏检了一半以上（recall 42.5%），误检率 30%。**
对于一个要"扣分、通报批评"的产品，这个精度**绝对不能上线**。如果把当前模型的 `bare` 判定直接用于扣分，将造成大规模误伤，必然引发学生投诉甚至法律风险。

**根因分析（推断）：**
1. **训练轮次严重不足**：仅 20 epoch（从 loss 曲线看 `cls_loss` 仍在 0.83 稳定下降，从未收敛），正常需 100-150 epoch。
2. **CPU 训练 + batch=4**：极慢且梯度噪声大。
3. **数据集只有 1930 张标注图**（据 `selfcheck.py` 注释），规模偏小。
4. **`cls_remap: true` + 类别设计缺陷**：把 `helmet` / `no helmet` 作为**独立目标检测类别**，而非**属性分类**。

> 💡 **模型架构层面的核心洞察（本文最重要的一条建议）**：
>
> 当前用**目标检测**同时解决"人车在哪"和"戴没戴盔"两个问题，这是**架构性错误**。
> - `helmet` 框面积中位数仅 0.00033（约为 `Cyclists` 框的 1/270），小目标检测极度困难；
> - `no helmet` 框面积 0.00015，更小，漏检率天然高；
> - "未戴盔"是一个**否定性概念**，没有物理边界，标注极不一致 → 这是 recall 只有 42% 的根本原因。
>
> **正确做法：分解为两阶段**
> 1. 检测 `Cyclists`（人车整体框，够大、够稳定）→ Recall 可轻松到 95%+
> 2. 对每个 `Cyclists` 框裁剪头部 ROI → 训练一个**二分类/多分类分类器**（helmet / no-helmet / 其它）
>
> 这样把"小目标检测"降维成"区域分类"，准确率可从 45% 提升到 85%+。详见 [§9](#9-算法与模型优化路线)。

## 2. 痛点分析与产品定位

### 2.1 真实痛点链条（用户视角）

```
现状痛点：
保安蹲守（人力成本高，无法覆盖所有时段/校门）
    ↓
学生不配合（"我不戴，你能拿我怎样？"）
    ↓
管理无抓手（无记录、无证据、无法教育、无法追责）
    ↓
无数据（不知道多少人不戴、哪些人反复违规、佩戴率趋势）
```

**核心洞察：保安的工作不是"抓人"，而是"教育 + 威慑"。**
产品不能做成"监控处罚系统"（学生会反感、学校难推），必须做成**"正向激励 + 温和提醒 + 有据可查"**。

### 2.2 产品定位（一句话）

> **面向师生的校园骑行安全行为积分平台**：用 AI 自动完成"发现 → 判定 → 决策"三步，管理员一键审批生效，学生小程序实时收到提醒与申诉通道。

### 2.3 设计原则（贯穿全文，必须遵守）

| 原则 | 具体含义 | 反面案例 |
|---|---|---|
| **P1 证据优先** | 任何惩罚必须有可追溯证据（图/帧/置信度/推理依据） | 直接扣分无证据 |
| **P2 三态保守** | 不确定就 `unknown`，绝不猜 | 二分类强制判定 |
| **P3 人工兜底** | AI 决策全部进入审批队列，无自动生效（可配置白名单） | AI 直接扣分 |
| **P4 正向激励** | 积分榜/荣誉/奖励与惩罚同等重要 | 只有惩罚没有奖励 |
| **P5 隐私最小** | 不做人脸识别，身份靠"账号绑定"而非"面部识别" | 上人脸库 |
| **P6 学生可申诉** | 每条处罚都有申诉入口，申诉需管理员二次处理 | 处罚无出口 |
| **P7 最小权限** | 学生只能看自己的；管理员分角色（辅导员/安保/校团委） | 所有管理员全能 |
| **P8 可解释** | 每次判定给出 reason_code 与可视化依据 | 黑箱判定 |

### 3.1 业务闭环全景

```
┌──────────────────────────────────────────────────────────────────────┐
│                          采集层（边缘设备）                          │
│  摄像头 / 树莓派 / 校门闸机  →  YOLOv8 推理  →  通行事件             │
│  ┌────────────┐   ┌──────────────┐   ┌───────────────────────────┐  │
│  │ 帧抽取     │──▶│ 身份关联     │──▶│ 证据包（帧+框+置信度）    │  │
│  │ 多路摄像头 │   │ 账号匹配     │   │ 加密上传                  │  │
│  └────────────┘   └──────────────┘   └───────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────┘
                                    ↓
┌──────────────────────────────────────────────────────────────────────┐
│                        事件处理层（后端）                           │
│  通行事件 → 身份绑定 → 风险聚合 → 【AI 决策引擎】                    │
│                                    ↓                              │
│                    ┌───────────────────────────────┐                │
│                    │  AI 决策输出（可解释）         │                │
│                    │  action + level + reason +    │                │
│                    │  confidence + evidence_refs   │                │
│                    └───────────────────────────────┘                │
│                                    ↓                              │
│                        审批队列（pending_review）                   │
└──────────────────────────────────────────────────────────────────────┘
                    ↓                              ↓
    ┌───────────────────────┐      ┌──────────────────────────────┐
    │  自动通道（低风险）    │      │  人工通道（中高风险）        │
    │  积分 -1 / 口头提醒   │      │  扣分 / 通报批评 / 奖励      │
    │  阈值内自动生效       │      │  管理员审批后可生效          │
    │  事后抽检 5%          │      │  需填理由 + 可调档位         │
    └───────────────────────┘      └──────────────────────────────┘
                    ↓                              ↓
┌──────────────────────────────────────────────────────────────────────┐
│                         触达层                                       │
│  现场大屏播报 → 小程序订阅消息 → 班级通知 → 辅导员 → 学生申诉       │
└──────────────────────────────────────────────────────────────────────┘
```

### 3.2 AI 决策的"分级自治"设计（关键）

**不要让 AI 一步到位决定"扣 3 分并通报批评"。** 采用**分级自治 + 人工兜底**：

| 等级 | 触发条件 | AI 自主权 | 审批要求 | 举例 |
|---|---|---|---|---|
| **L0 静默** | `unknown` / 置信度 < 阈值 | 仅记录 | 无 | 遮挡、看不清 |
| **L1 提示** | 首次轻微违规、置信度高、身份可识别 | 生成"提醒"建议，自动生效（仅口头/站内提醒，不扣分） | 无（抽检 5%） | 首次未戴盔 → 温柔提醒 |
| **L2 记分** | 短期内重复、置信度高、身份确定 | 生成扣分建议（分值 ≤ 1） | 管理员批量确认 | 30 天内第 2 次 → -1 分 |
| **L3 严惩** | 严重/高频违规 | 生成通报建议 | **必须逐条人工审批** | 第 4 次或拒戴逃逸 → -3 分 + 通报批评 |
| **L4 奖励** | 连续合规 / 满分周期 / 主动上报 | 生成奖励建议 | 管理员审批 | 连续 30 天合规 → +2 分 + 表彰 |

**自治策略的关键参数（可后台配置）：**

```yaml
decision_policy:
  auto_approve:
    - level: L1
      max_score_delta: 0        # 绝不扣分
      sample_rate: 0.05         # 5% 抽检复核
    - level: L2
      max_score_delta: -1
      require_identity_confidence: 0.8
      require_model_confidence: 0.7
  human_required:
    - level: L3
      require_reason: true      # 审批人必须填写理由
      allow_downgrade: true     # 允许管理员降档（L3 -> L2）
      allow_upgrade: false      # 不允许升档（防止过度处罚）
  risk_gates:                  # 风险熔断闸门
    - 同一学生单日扣分 > 5 分时，全部转人工
    - 单日全校处罚事件 > 50 条时，暂停自动通道
    - 模型版本 mAP < 0.8 时，自动通道只允许 L0/L1
```

### 3.4 审批工作流

| 状态 | 含义 | 可操作 |
|---|---|---|
| `pending_review` | AI 已决策，等待人工 | 批准 / 驳回 / 降档 / 升级 / 批量批准 |
| `approved` | 人工批准，已生效 | 查看 |
| `rejected` | 人工驳回（判定有误） | 查看 + **回流训练集** |
| `adjusted` | 人工调整了档位后批准 | 查看 |
| `auto_approved` | 自动通道生效 | 查看 + 抽检可撤销 |
| `appealing` | 学生申诉中 | 处理申诉 |
| `appeal_upheld` | 申诉成立，撤销处罚 + 补偿积分 | - |
| `appeal_rejected` | 申诉不成立 | 通知学生 |
| `expired` | 超时未审批（默认 7 天）自动失效 | - |

**审批 SLA 与超时策略：**
- L1/L2：24 小时内处理完，逾期自动批量通过（若仍在策略允许范围）
- L3：24 小时内必须处理，逾期升级通知（短信/企业微信）到上一级管理员
- 申诉：3 个工作日内答复

## 4. "这是谁的车"身份识别方案（关键难点）

这是整个项目**技术上最核心、也最能体现竞赛价值**的模块。下面给出**四层递进方案**，建议**分阶段实施**。

### 4.1 方案总览

```
┌─────────────────────────────────────────────────────────────┐
│  L4 层：校园一卡通 / 校园卡绑定（最可靠，但依赖校方系统）     │
│    车牌/车辆二维码 ↔ 学生学号 一对一登记                      │
├─────────────────────────────────────────────────────────────┤
│  L3 层：车牌 OCR + 车辆特征（主力方案）                       │
│    电动车车牌（浙/苏/皖…地方牌照 + 校园自定义编号牌）          │
├─────────────────────────────────────────────────────────────┤
│  L2 层：Helmet 自适应蓝牙 / 车载 NFC 标签（增强手段）        │
├─────────────────────────────────────────────────────────────┤
│  L1 层：轨迹 + 时空关联 + 同学关系图（兜底补全）              │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 L4 层：校园车辆登记系统（战略层，必须与学校谈）

**这是唯一 100% 准确且零技术风险的方案，也是本项目最大的"制度性创新点"。**

**流程设计：**
1. 学校保卫处（或学工部）开放"校园电动车登记"服务；
2. 学生用小程序扫码/上传 **行驶证 + 车辆照片 + 车牌照片** 提交登记；
3. 管理员在后台审核通过，生成 **车辆档案**（vehicle_id ↔ 学号 ↔ 车牌号 ↔ 车型）；
4. 车辆在车把安装 **校园统一识别牌**（二维码 / 校园统一蓝色号牌 / NFC 贴纸）；
5. 校门摄像头读取识别牌 → 精确绑定学号。

**为什么强烈建议：**
- 现实中学校**没有**能力维护一张"车 → 人"的对应表，而**电动车的行驶证是现成的法定凭证**；
- 登记一次，永久有效，是**一次性成本、长期收益**的制度设计；
- 直接解决"外卖员/教职工/访客"等非学生车辆无法归属的问题；
- 在竞赛答辩中，这是**从"技术项目"跃升为"治理方案"**的关键论据。

**不做这一层的降级方案：** 见 L1/L2/L3。

### 4.3 L3 层：车牌 OCR + 车辆特征（主力技术方案）

#### 4.3.1 车牌识别

**关键现实认知：**
> 校园内电动车车牌状况很差：大量为**校园自编号牌**（如"东门 037"）、**本地牌照电动自行车牌**（如"合肥 A12345"）、部分**无牌/遮牌**、部分为**外卖骑手的三轮车/外卖箱车**（无牌）。

因此车牌 OCR 需要**分类型处理**：

| 类型 | 识别方式 | 置信度权重 |
|---|---|---|
| 标准蓝牌电动车牌 | PaddleOCR / CRNN + 字符字典 | 0.9 |
| 校园自编号牌 | OCR + 数字/字母约束 + 校园点位字典 | 0.85 |
| 无牌车 | 车辆外观特征 + 轨迹 | 0.3 |
| 外卖/快递三轮 | 车体颜色 + 保温箱特征 + 骑手制服 | 0.4（标记为"非校内人员"） |

**技术方案：**
- **检测**：YOLO 增加 `plate` 类别（或独立轻量检测模型），训练数据可从公开车牌数据集 + 校内自采；
- **识别**：PaddleOCR（PP-OCRv4）轻量版，或 DBNet + CRNN；
- **后处理**：字符级字典约束（省份简称 + 字母数字）、几何校正（车牌矫正）、置信度 = 字符置信度均值 × 框置信度。

#### 4.3.2 无牌车的兜底：车辆外观特征向量

为每辆车维护一个 **128 维外观特征向量**（ReID 风格）：

```
vehicle_signature = hash(
    车辆颜色直方图(H/S 直方图 64维) +
    车架/车身形状上下文特征(来自检测框的宽高比、轮廓) +
    挡风被/挡风罩特征 +
    车筐/后座特征 +
    挂件/贴纸图案 CNN 特征(可选)
)
```

**匹配流程：**
1. 每次通行时，从 `Cyclists` 框裁剪车辆区域，计算外观特征；
2. 与"该学生已登记车辆"的特征库做余弦相似度匹配；
3. 若最高相似度 > 阈值（如 0.82）且与第二名差距 > 0.05 → 判定归属；
4. 连续多次通行都匹配到同一车 → 逐步**学习**该学生的车辆特征，形成"未登记车辆也能认出来"的正反馈。

> 💡 **这是一个渐进式能力**：随着运行时间增长，系统会自发积累"哪些车属于哪些学生"的关联，无需学生主动登记。这是产品长期壁垒。

### 4.4 L2 层：蓝牙 / NFC 增强（可选增强项）

| 方案 | 原理 | 成本 | 有效性 |
|---|---|---|---|
| **Helmet 自适应蓝牙信标** | 头盔内置 BLE 广播 MAC/设备 ID，闸机旁信标扫描 | 中（头盔供应商定制） | ⭐⭐⭐⭐⭐ 极高 |
| **车载 NFC 贴纸** | 车把贴 NFC 卡，靠近读卡器即读 ID | 低（几毛钱/张） | ⭐⭐⭐⭐ 高 |
| **车载二维码** | 车把二维码，闸机扫码枪/摄像头识别 | 最低 | ⭐⭐⭐⭐ 高（但可能被撕） |
| **UWB 精确定位** | 超宽带定位，精确到 0.3m | 高 | ⭐⭐⭐⭐⭐ 极高（可同时做轨迹） |

**推荐组合：** `车载二维码/校园统一号牌（兜底，视觉可检测）+ NFC（可选）`

理由：二维码可以被检测模型一起识别（新增 `qr_plate` 类别），**不增加额外硬件成本**，且与"车辆登记"制度天然配套。

### 4.5 L1 层：时空轨迹 + 同学关系图（纯软件兜底方案）

当以上都失败时（无牌、不扫码、模型未识别出车），用**图算法推断**：

**核心思想：同一个人的车辆在多天、多摄像头下会表现出"共现规律"。**

#### 4.5.1 车辆共现矩阵

对所有"未识别车辆"生成匿名车辆 ID（基于轨迹聚类的临时 ID），统计：

```
co_occurrence[vehicle_A][vehicle_B] = 共同出现的时间窗口数量
```

- 若车辆 A 与 车辆 B（已识别为学生张三）**在 70% 以上的出现时刻同时出现**（如同进同出宿舍区、教学楼），则 A 极可能也属于张三或张三室友。
- 用 **Jaccard / 余弦相似度** 度量，计算时间窗口（5 分钟粒度）的共现率。

#### 4.5.2 宿舍/班级归属推断

- 引入 **宿舍楼门禁记录**（若校方系统可对接）：车辆 A 出现在某宿舍楼门禁记录的持卡人 → 直接绑定学号。
- 若无法对接：用 **时间模式聚类**——A 的通行时间分布与 B 的高度重合（早 7:50 / 晚 21:30 固定），则关联。

### 4.6 身份置信度融合公式

多个证据源采用**对数似然比加权融合**（Log-Opinion Pool）：

```
logit(P_identity) = Σᵢ wᵢ · log( pᵢ / (1 - pᵢ) )

p_plate   = 0.95   (车牌 OCR 高置信度)
p_qr      = 0.95   (二维码)
p_nfc     = 0.98   (NFC 读卡)
p_appearance = 0.70 (外观特征匹配)
p_cooccur = 0.45   (共现推断)
p_none    = 0.05   (无任何证据)
```

**决策阈值：**

| 身份置信度 | 处理方式 |
|---|---|
| ≥ 0.85 | 自动绑定，直接进入 AI 决策 |
| 0.60 ~ 0.85 | 生成"疑似"记录，管理员快速确认（列表批量点选） |
| < 0.60 | 不进入惩罚决策，转"待识别车辆"池，人工登记 |

> ⚠️ **重要设计原则**：**身份置信度不足时，绝不惩罚**。宁可漏过，不可错伤。这与 §2.3 的 P2/P3 原则一致。

### 6.3 技术选型建议

| 层 | 现状 | 生产建议 | 理由 |
|---|---|---|---|
| API | FastAPI | **保持** | 异步、类型提示、Pydantic 校验，代码质量已到位 |

| ORM | 裸 SQL | **SQLAlchemy 2.0** | 现有多处手写 SQL 拼接（虽参数化），加表时易错 |
| 队列 | 无 | **Celery + Redis**（或 RQ/Arq） | 通知、报表、异步 OCR 都需异步化 |
| 文件 | 本地 | **MinIO / OSS** | 证据图片/视频需可访问、可归档 |
| 推理 | CPU | **GPU（边缘盒子 + 服务器）** | recall 提升 + 头部分类后需更强算力 |
| 部署 | 手工 | **Docker Compose → K8s** | 比赛演示需一键启动 |
| 监控 | 无 | **Prometheus + Grafana** | 设备在线率、队列积压、模型效果 |

> 💡 **比赛演示的务实建议**：技术栈越简单越好。**保留 FastAPI + SQLite（改 WAL 优化）或换 PostgreSQL + Docker Compose**，不要在比赛期间引入 K8s。架构文档写清楚"生产可演进到 K8s"即可。

## 8. AI 决策引擎设计

### 8.1 设计目标

> **AI 决策不是"用 LLM 拍脑袋"，而是"规则引擎做确定性判断 + LLM 做自然语言解释 + 人工做最终把关"。**

这个设计在答辩时极其有说服力：**既体现了 AI 的能力，又体现了对 AI 不可靠性的敬畏。**

### 8.2 三层架构

```
┌──────────────────────────────────────────────────────┐
│  L-3 层：自然语言解释生成（LLM，可选）                 │
│  输入：结构化决策因子 + 规则命中                        │
│  输出：个性化、通俗、针对学生的话术                     │
│  ⚠️ 只解释，不决策；输出必须过"敏感词/越权"校验         │
├──────────────────────────────────────────────────────┤
│  L-2 层：规则决策引擎（确定性、可测试、可审计）         │
│  规则 DSL → 风险聚合 → 档位判定 → 动作映射             │
│  确定性 100%，可单元测试，可版本化，可回放              │
├──────────────────────────────────────────────────────┤
│  L-1 层：事实层（来自检测/身份/积分数据）               │
│  passes / identities / score_ledger / cooccurrence      │
└──────────────────────────────────────────────────────┘
```

### 8.3 规则 DSL 设计

```python
# app/services/decision/rules.py
from dataclasses import dataclass
from typing import Callable, Any


@dataclass
class Fact:
    """事实层暴露给规则引擎的原子事实。"""

    model_confidence: float  # 模型置信度
    identity_confidence: float  # 身份置信度
    helmet_status: str  # helmeted|bare|unknown
    violation_count_30d: int  # 近30天违规次数
    violation_count_7d: int
    total_passes_30d: int
    streak_days: int  # 连续合规天数
    score_balance: int
    peak_hour: bool  # 是否高峰期
    repeat_same_point: bool
    appeal_history_upheld: int  # 历史申诉成立次数（影响信任度）


# 规则函数签名统一
Rule = Callable[[Fact, dict], tuple[bool, dict]]
#     ↑ 命中判定   ↑ 补充因子/理由


def rule_repeat_within_30d(f: Fact, ctx: dict) -> tuple[bool, dict]:
    """近30天重复违规"""
    hit = f.violation_count_30d >= 1
    return hit, {"evidence": f"近30天违规 {f.violation_count_30d} 次"}


def rule_high_confidence(f: Fact, ctx: dict) -> tuple[bool, dict]:
    """高置信度（模型 + 身份双高）"""
    hit = f.model_confidence >= 0.70 and f.identity_confidence >= 0.80
    return hit, {"evidence": f"模型 {f.model_confidence:.2f} / 身份 {f.identity_confidence:.2f}"}


def rule_first_offense(f: Fact, ctx: dict) -> tuple[bool, dict]:
    """首次违规（从宽）"""
    hit = f.violation_count_30d == 0
    return hit, {"evidence": "首次违规"}
```

### 8.4 档位决策矩阵

```python
def decide_level(f: Fact, policy: dict) -> tuple[str, str, int]:
    """返回 (level, action, score_delta)。确定性纯函数，可单测。"""

    # —— 风险闸门（先于一切规则）——
    if f.helmet_status != "bare":
        return ("L0", "none", 0)
    if f.identity_confidence < 0.60:
        # 身份不确定 → 不惩罚，只记录待识别
        return ("L0", "none", 0)
    if f.model_confidence < policy.get("min_model_conf", 0.60):
        return ("L0", "none", 0)

    # —— 分档（有序判定，先命中先返回）——
    if f.violation_count_30d >= 3 or f.appeal_history_upheld >= 2:
        return ("L3", "report", policy.get("l3_score", -3))
    if f.violation_count_30d >= 1:
        delta = policy.get("l2_score", -1)
        return ("L2", "deduct_score", delta)
    # 首次：温和提醒
    return ("L1", "remind", 0)
```

### 8.5 LLM 解释层（增强项）

**用途：生成学生看得懂、愿意接受的话术。** 这是提升"接受度"的关键。

```
系统提示：
你是校园安全教育助手。给定一条处罚决策及其结构化因子，
生成一句面向学生的话术。要求：
1. 客观陈述事实，不指责人格；
2. 指出可改进的具体行为；
3. 给出正向出口（如何快速恢复积分）；
4. 语气平和，60 字以内；
5. 不出现任何"罚款""扣钱""处罚个人"表述；
6. 不承诺任何超出系统权限的承诺。

输入（JSON）：
{"level":"L2","action":"deduct_score","score_delta":-1,
 "factors":[{"name":"历史违规次数","value":1,"evidence":"近30天1次未戴盔"},
            {"name":"模型置信度","value":0.93,"evidence":"no_helmet conf=0.93"}],
 "streak_days":12,"score_balance":95}

输出：
"检测到您本次骑行未佩戴头盔，近30天内第2次，已扣除1分文明积分。
您已连续安全骑行12天，佩戴头盔即可恢复积分。申诉入口：我的-处罚记录-申诉。"
```

**安全护栏（必须实现）：**
- LLM 输出仅用于 `message` 字段，**不参与 `level`/`action`/`score_delta` 决策**；
- 输出经敏感词过滤 + 长度校验；
- 生成失败时回退到**模板文案**（预置 20+ 条）；
- 记录 prompt 与输出到 `decision_logs`，可回溯。

### 8.6 决策可回放性（答辩加分项）

```python
def replay(decision_id: str) -> dict:
    """用当前策略重放历史决策，输出差异报告。

    用于：策略调整前的影响评估、答辩演示"AI 决策可审计"。
    """
    d = get_decision(decision_id)
    f = rebuild_facts(d.event_id)  # 从事实层重建
    new = decide_level(f, load_policy())  # 用当前策略重算
    return {"original": {...}, "replayed": new, "changed": new != original}
```

## 9. 算法与模型优化路线

### 9.1 核心问题诊断

| 问题 | 现状 | 影响 | 解决方案 |
|---|---|---|---|
| **模型精度不足** | mAP50=0.457, recall=0.425 | 无法上线 | 见 §9.2、§9.3 |
| **训练不充分** | 仅 20 epoch，loss 未收敛 | 精度天花板 | 训练至 150 epoch + 早停 |
| **训练设备差** | CPU, batch=4 | 慢、梯度噪声大 | GPU（Colab/租卡），batch=16 |
| **小目标检测** | helmet 框面积中位 0.00033 | 漏检主因 | 见 §9.3 两阶段法 |
| **否定性类别** | `no helmet` 无物理边界 | 标注不一致 | 见 §9.3 改二分类 |
| **数据量少** | 约 1930 张标注 | 泛化差 | 见 §9.4 数据工程 |
| **场景域差异** | 公开数据集 vs 校园实拍 | 部署掉点 | 见 §9.4 自采数据 + 域适配 |
| **多骑行者** | 1120/1930 图含 2+ 骑行者 | 归属错乱 | 跟踪 + 归属算法（已部分实现） |
| **缺车牌类别** | 无 `plate` | 无法识别车 | 新增类别或独立 OCR 模型 |

### 9.2 阶段一：把现有模型训好（1-2 周）

```
训练配置 v3：
  model:      yolov8m.pt（或 yolov8s.pt，兼顾速度）
  epochs:     150（early stopping patience=30）
  imgsz:      640（当前 480 太小，头部框极小会丢）
  batch:      16（GPU）
  device:     0 / cuda
  optimizer:  auto
  lr0:        0.01
  hsv_h:      0.015 → 0.025（光照差异大）
  hsv_s:      0.7 → 0.8
  degrees:    0 → 5（轻微旋转）
  mosaic:     1.0
  scale:      0.5
  translate:  0.1 → 0.15
  copy_paste: 0.5   ← 关键：增加头部样本的多样性
  cls:        0.5 → 0.8  ← 分类损失加权（类别不均衡时有效）
```

**目标指标：**

| 指标 | 起点 | v3 目标 | 备注 |
|---|---|---|---|
| mAP50 | 0.457 | ≥ 0.80 | |
| mAP50-95 | 0.253 | ≥ 0.55 | |
| Recall(bare) | — | ≥ 0.80 | **最关键**：漏检少戴盔 = 漏罚 |
| Precision(bare) | — | ≥ 0.85 | 误罚成本更高，宁可漏 |

**类别不均衡分析（必做）：**
```python
# 统计各类别实例数（训练集）
# 典型分布（从注释推断）：
#   Cyclists  ≈ 1930 × 2.9 ≈ 5600
#   helmet    ≈ 1930 × 0.86 ≈ 1660
#   no helmet ≈ 1930 × 0.23 ≈ 440   ← 严重稀少
```
`no helmet` 样本稀少是 recall 低的直接原因。解决方案：
1. `copy_paste` 增强复制稀有类；
2. 专门构造 `no helmet` 增强样本（从 helmet 图像挖除头部区域贴背景）；
3. 采样器 `WeightedRandomSampler` 或 ultralytics 的 `fraction` 调整；
4. **根本上用 §9.3 的两阶段法绕开**。

### 9.3 阶段二：两阶段架构重构（强烈推荐，2-3 周）

#### 9.3.1 问题本质

```
当前（单阶段检测）：
  图像 → YOLO → [Cyclists框] + [helmet框] + [no helmet框]
                                  ↑
                        面积中位 0.00033 / 0.00015
                        = 单张 640×640 图上约 6×7 / 4×4 像素
                        → 小目标检测极限 → recall 42%

重构（检测 + 属性分类）：
  图像 → YOLO → [Cyclists框]（足够大，recall 可到 95%+）
                ↓ 裁剪头部 ROI
        头部图像 → 分类器 → helmet / no helmet / ambiguous
```

**收益：**
- 头部裁剪图放大到 64×64 甚至 128×128，分类任务难度**下降一个数量级**；
- 不再需要检测"没有的东西"（否定性类别），标注一致性大幅提升；
- 分类器可用轻量 CNN（MobileNetV3/EfficientNet），边缘设备可实时跑；
- `ambiguous` 类吸收遮挡/模糊样本，避免强制误判。

#### 9.3.2 头部 ROI 提取规则

```python
def extract_head_roi(rider_box: np.ndarray, img: np.ndarray, top_ratio: float = 0.45) -> np.ndarray:
    """从骑行者框上部裁剪头部区域。

    依据（来自 selfcheck.py 标注统计）：
      - helmet 中心相对骑行者框的 rel_y 中位 ≈ 0.10，p90 ≈ 0.16
      - 因此取上部 45% 覆盖了绝大多数真实头部
    """
    x1, y1, x2, y2 = rider_box
    h = y2 - y1
    # 头部框中心横向在骑行者框内 30%-70% 区间（更精准）
    head_x1 = x1 + (x2 - x1) * 0.25
    head_x2 = x2 - (x2 - x1) * 0.25
    head_y1 = y1
    head_y2 = y1 + h * top_ratio
    roi = img[int(head_y1) : int(head_y2), int(head_x1) : int(head_x2)]
    return cv2.resize(roi, (128, 128))
```

#### 9.4.2 校内自采 SOP（关键）

```

  · 位置：东校门、西校门、教学区路口（3+ 点位，覆盖不同光照）
  · 时段：早高峰(7:30-9:00)、平峰、晚高峰(17:00-19:00)、夜间(带灯)

  · 数量：每类别（helmet/no helmet）× 每角度 × 每距离 ≥ 50 张

标注规范（必须统一，否则标注不一致=模型不一致）：
  · Cyclists：人 + 车的最大外接框
  · helmet：头盔外框（不是人脸），只标头盔本身
  · no helmet：头部外框（头发+脸的范围），不标整人
  · 遮挡超过 50% 的头部标 ignore（不参与训练）
  · 篮中/手持头盔 → 标 helmet 框但位置在底部（依赖归属算法排除）
  · 双人同框 → 两组 Cyclists，各自独立头部

质检：双人标注 + 第三人抽检 20%，一致率 < 90% 需重标
```

#### 9.4.3 数据集划分（避免泄漏！）

```
⚠️ 常见错误：同一段视频的连续帧被分到 train 和 val → 验证集虚高

正确做法：
  · 按"视频片段/采集时段"分组划分，而非按图片随机划分
  · train:val:test = 7:2:1，按 session 分组
  · 时间维度外推测试：额外保留"某一天的完整数据"作为时序测试集
  · 测试集单独标注，作为最终验收依据（不参与任何训练与调参）
```

## 12. 安全、隐私与合规

### 12.1 法律与合规基线（必须了解）

| 法规 | 关键要求 | 对本项目的影响 |
|---|---|---|
| 《个人信息保护法》 | 最小必要、知情同意、个人信息处理记录 | 必须有隐私政策与同意流程 |
| 《民法典》人格权编 | 肖像权、隐私权 | 不得用于非授权目的 |
| 《道路交通安全法》 | 骑乘必须戴头盔（地方法规更严） | 本项目是**配合执法**，非执法主体 |
| 教育部《学生伤害事故处理办法》 | 学校管理责任 | 需与学校制度对齐 |
| 《网络安全法》《数据安全法》 | 数据分类分级、日志留存 | 证据留存需有期限策略 |

### 12.2 隐私保护设计（关键差异化点）

| 数据类型 | 存储 | 访问控制 | 保留期 | 说明 |
|---|---|---|---|---|
| 通行事件（无身份） | 明文 | 所有管理员 | 1 年 | 统计用 |
| 身份关联结果 | 明文 | 身份管理 + 审批人 | 1 年 | |
| **证据截图（含人脸）** | **加密 + 访问审计** | 审批人 + 安全员，**每次访问留痕** | **90 天**（超期自动删除） | ⚠️ 最敏感 |
| 视频片段 | 加密 | 同上 | 30 天 | |
| 学生档案 | 明文 | 本人 + 辅导员 | 长期 | |
| 积分记录 | 明文 | 本人 + 管理员 | 长期 | |
| 申诉材料 | 加密 | 申诉处理人 | 1 年 | |

**关键设计：**
1. **不做人脸识别**（P5 原则）。身份靠"车辆登记 + 账号绑定"，这是**用制度替代技术**，规避了最大的法律风险。
2. **证据快照加密存储**，访问需二次鉴权 + 每次访问写 `audit_logs`。
3. **证据自动过期删除**（90 天），后台显示"证据将于 X 日后自动删除"。
4. **抓拍用途告知牌**：校门显著位置张贴"本区域进行安全行为监测"的标识（配合《个人信息保护法》第 17 条告知义务）。
5. **学生知情同意**：首次使用小程序时展示《校园骑行安全监测知情同意书》，勾选后方可使用。

### 12.3 安全实现要点

```python
# 1. 密码/JWT
- 密码: bcrypt (cost=12) 或 Argon2
- JWT: HS256/RS256, access_token 2h, refresh_token 7d
- refresh_token 存 Redis，支持主动吊销

# 2. 接口安全
- 限流: Redis + 滑动窗口（登录 5次/分钟，查询 60次/分钟，上传 10次/分钟）
- 越权防护: 每个接口显式校验资源归属（学生只能访问自己的记录）
- SQL 注入: 已用参数化（保持），禁止 f-string 拼接（现有代码已合规）
- 文件上传: 校验真实 MIME（magic bytes），不用后缀名判断；尺寸/像素上限（已实现两层限流）
- CORS: 白名单精确配置，禁止 `*` + credentials

# 3. 审计
- 所有写操作记录：操作人、时间、IP、参数摘要、变更前后
- 证据访问单独审计（谁看了谁的抓拍）
- 审计日志只增不改，定期归档

# 4. 密钥
- .env 管理，用 python-dotenv 加载，绝不入库
- 生产用环境变量 / Vault
- 已有做法 ✅：_weights_display 只返回相对路径，不泄露绝对路径
```

### 12.4 越权与数据隔离的关键实现

```python
# 学生只能看自己的记录 —— 在 service 层强制，而非仅靠前端隐藏
def get_event_for_user(conn, event_id: str, user: User) -> dict:
    row = conn.execute("SELECT * FROM events WHERE event_id=?", (event_id,)).fetchone()
    if row is None:
        raise NotFound()
    if user.role == "student":
        if row["student_id"] != user.student_id:
            # 越权访问返回 404 而非 403，避免泄露"该记录存在"
            raise NotFound()
    elif user.role == "counselor" and not user.covers(row["student_id"]):
        raise NotFound()
    return dict(row)
```

```
答辩时最能打动评委的三件事（建议集中资源打磨）：

1️⃣ 「这是谁」—— 身份识别

2️⃣ 「AI 决策 + 人工审批」—— 治理闭环
   演示：AI 给出 L1/L2/L3 分级建议 + 可解释因子，管理员一键调整档位；
        展示策略模拟器：把扣分从 -3 改成 -2，用历史 30 天数据推演影响面。
   价值：展示了"AI 参与治理但不越权"的设计智慧，比纯技术炫技高一个层次。

3️⃣ 「正向激励」—— 落地可行性
   演示：积分商城、班级排行、勋章；对比传统"抓人罚款"的方案。
   价值：直接回应"学校会不会用"的现实拷问，让评委看到落地思维。
```

| A-23 | `docs文档/` | **空目录** | 补充架构文档、API 文档、算法说明、用户手册 |
| A-24 | `app/main.py` | `_all_heartbeats` 一次性拉全部心跳 | 心跳表会无限增长，需定期清理（保留最近 N 条 per source） |
| A-25 | `app/detect.py` | `occurred_at` 用 `time.gmtime()` + `+00:00` 硬编码 UTC | 与 `store.now_iso()` 的 UTC 一致，但业务应存**本地时区**以便按日统计（建议统一存 UTC + 时区偏移，展示层转换） |

## 结语

这个项目已经具备了**扎实的技术底座**（工程规范度、判定逻辑严谨性、前端交互质量都高于同类学生项目），但目前停留在"**检测工具**"层面。

要让它成为"**校园头盔检测提醒助手**"并具备真正的落地价值，需要补齐三条主线：

```
① 身份主线：这是谁？
   └─ 车辆登记制度（最强）+ 车牌OCR + 外观特征 + 共现图谱（技术兜底）
   
② 治理主线：怎么办？
   └─ AI 分级决策（规则引擎）+ 人工审批 + 积分台账 + 申诉通道 + 正向激励
   
③ 触达主线：怎么让他知道？
   └─ 现场播报 + 小程序订阅消息 + 班级通知 + 排行榜 + 积分商城
```

**最关键的三个判断：**

1. **不要用当前模型直接做处罚。** recall 0.425 意味着漏检一半以上，precision 0.696 意味着误伤三成。必须先做 §9 的两阶段重构 + 校内数据补齐。这是**能否上线的生死线**。

2. **身份识别是本项目最大的差异化机会，也是最大的风险点。** 大多数同类项目只能做到"检测到有人没戴盔"，如果你们能把"这是谁"解决好（哪怕先用最简单的车辆登记 + 车牌 OCR），项目的价值会提升一个量级。

3. **不要把它做成"监控处罚系统"。** 学校要的是"减负 + 教育效果"，学生要的是"不被冤枉 + 有正向出口"。AI 自动决策 + 人工审批 + 申诉 + 正向激励这套组合，既回应了技术评委，也回应了学校和学生的真实诉求——**这才是能让项目真正落地的设计**。

祝项目顺利。这份文档可以作为后续所有开发的唯一事实来源。
