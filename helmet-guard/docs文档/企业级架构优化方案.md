## 摘要：一句话结论

**后端分层与测试质量已达企业级水准（覆盖率 81%、domain 层零 I/O、mypy strict 全绿），真正的债集中在三处：**

1. **前端组件巨石** —— `views/decisions/List.vue` 1072 行、`views/identities/Students.vue` 612 行、8 个组件的 `<style>` 块超 100 行上限（最大 352 行）
2. **事务边界散落在路由层** —— `try/commit/except/rollback` 在 5 个路由文件中重复，路由层还直接写 SQL
3. **`main.py` 是 565 行的四合一** —— 路由 + 原生 SQL + 健康检查 + 中间件混在一个文件

**外加 1 个致命功能缺口**：`/api/v1/auth/*` 完全缺失 → 管理后台当前**无法登录**，整个前端是死的。

**建议顺序**：先补认证（解锁全站）→ 再清架构债（分 4 批，每批可独立验收）→ 最后补功能缺口。

## 第二部分：问题清单（按严重度）

### 🔴 P0-1：认证 API 缺失 —— 全站不可用

| 项 | 事实 |
|---|---|
| 前端调用 | `api/auth.ts` 4 个接口：`/v1/auth/login`、`/refresh`、`/logout`、`/me`（`baseURL='/api'` → `/api/v1/auth/*`） |
| 后端实际 | **0 个**（OpenAPI 32 条路径无一条 auth） |
| 后果 | 登录永远失败 → 路由守卫重定向 → **管理后台完全不可用** |
| 已有资产 | `core/security.py` JWT 签发/校验 + bcrypt 已就绪；`core/deps.py` 的 `CurrentUserDep`/`require_roles` 已就绪；`users` 表已有 `openid/username/phone/role/status` |
| 缺什么 | 路由层 + 仓储 + 服务 + schema + `users.password_hash` 列 + `admin/reviewer/observer` 三个角色枚举 |

**额外发现（枚举不全）**：`USER_ROLE_VALUES` 只有 6 值，但 `require_roles` 与前端 `UserRole` 实际用 9 值 ——
`admin` / `reviewer` / `observer` 三个角色**此前无法落库**（建账号会因枚举校验失败报错）。
→ 必须走迁移补齐，否则 RBAC 是假的。

### 🔴 P0-2：事务边界在路由层（架构性问题）

**现状**：事务模板 `try: ... session.commit() / except Exception: session.rollback(); raise` 散落在 **5 个路由文件**：

```
app/api/v1/identity.py    3 处（bind / ignore / import）
app/api/v1/appeals.py     3 处（resolve / submit）
app/api/v1/decisions.py   3 处（approve / reject / batch）
```

**同时**：`appeals.py` 的路由函数**直接写 SQL**（`select(Appeal).order_by(...)` + `session.execute(...)`），
并在函数体内 `from sqlalchemy import select as _select`（函数内 import）+ 留有死代码：

```python
statement_rows = AppealRepository(session).list_by_student("", limit=0, offset=0)
_ = statement_rows          # ← 查询了然后丢掉，纯死代码
```

**这违反 AGENTS.md 开发流程**：路由层不应含业务逻辑；仓储层才该碰 SQL。

**例外（正确）**：`services/scoring/ledger.py` 自己管事务（`BEGIN IMMEDIATE` + 锁重试）——
这是唯一正确范式，其余路由层应向它看齐。

### 🔴 P0-3：`main.py` 565 行四合一

`app/main.py` 同时承担：

| 职责 | 行数区间 | 问题 |
|---|---|---|
| FastAPI 实例 + lifespan | 48-70 | 启动建表逻辑混在应用装配里 |
| 路由注册（4 个 `suppress(Exception)`） | 82-105 | **静默吞异常** —— 导入失败则路由不注册且无报错 |
| 自查上传体限制中间件 | 108-190 | 83 行中间件与应用装配混排 |
| 健康检查（`_model_status` / `_capture_status` / `_db_status`） | 195-345 | 150 行，含原生 SQL |
| 7 个遗留 API（sources/stats/events/review/alerts/self-check） | 373-565 | 走 `sqlite3` 原生连接，与 ORM 层并存 |

**`suppress(Exception)` 的具体危害**：我实测过 —— `from app.api.v1.dashboard import router` 单独导入是成功的，
但如果这个文件有任何语法/导入错误，`main.py` 会**静默跳过注册**，服务照常启动，
只有前端 404 时才发现。这是典型的「静默失败」反模式，必须改为「注册失败即启动失败」。

### 🟠 P1-3：令牌体系未完全落地

`design.md` §9.2 要求**双阻尼物理**（`--ease-overdamped` / `--ease-underdamped`），
但 `design-tokens.scss` 里是：


另：`design.md` §4.3 要求暗色字重走 `--font-weight-*` 令牌，

## 第三部分：实施方案

### 3.1 总体策略：四个批次，每批可独立验收与回滚

```
批次 A（解锁）    认证 API + 枚举补齐        ← 不做则后面全部无法端到端验证
      ↓
批次 B（后端清债）main.py 拆分 + 事务下沉 + 路由层去 SQL
      ↓
批次 C（前端清债）巨石拆分 + 令牌体系修正 + 死代码清理
      ↓
批次 D（补功能）  积分 API + P3-3 页 + WebSocket + 小程序
```

**执行顺序已确认（2026-11-17）**：先 A+B+C 再 D —— 在屎山地基上补功能只会让债滚雪球。

**覆盖率门槛渐进策略**（已确认）：

| 阶段 | 门槛 | 前置条件 |
|---|---|---|
| 批次 A 结束 | **75** | 新增 auth 测试后自然达标 |
| 批次 B 结束 | **80** | 补 `main.py` 拆分后的健康检查测试 |
| 批次 C 结束 | **85** | 前端无覆盖率概念；后端补 `appeals`/`decisions` 路由测试 |

> ⚠️ **禁止靠删 `omit` 或加 `pragma: no cover` 凑覆盖率** —— 只能靠补测试。

**关键原则**：批次 B/C 是**纯重构**，行为等价，由 319 个既有测试 + 81% 覆盖率兜底，重构风险可控。
批次 A/D 是新功能，需要新测试。

### 批次 B：后端架构清债（P0-2 + P0-3）

#### B-1. 修 `suppress(Exception)` 静默失败

**现状**：`main.py` 4 处 `with suppress(Exception): from ... import router; app.include_router(...)`

**问题**：导入失败 → 路由静默不注册 → 服务正常启动 → 前端 404 → 排查困难。

**方案**：改为「导入失败即启动失败」，但保留**可选路由**的语义（若某个业务模块尚未实现，允许跳过）——
需要一个显式白名单，而不是静默吞异常。

```python
# 目标形态（示意）
_OPTIONAL_ROUTERS = ("identity", "decisions", "dashboard", "appeals", "auth")
for name in _OPTIONAL_ROUTERS:
    module = importlib.import_module(f"app.api.v1.{name}")
    app.include_router(module.router)
# 任一模块导入失败 → 直接抛异常 → uvicorn 启动失败 → 立刻可见
```

并加测试断言 OpenAPI 中确实存在这些路径（防止未来再次静默丢失）。

#### B-2. 拆分 `main.py`（565 行 → 目标 < 200 行）

```
app/main.py                      ← 只做：应用装配 + 路由注册 + 中间件挂载
app/api/v1/system.py             ← /health + /api/v1/sources + /api/v1/stats
app/api/v1/events.py             ← /api/v1/events + /api/v1/events/{id}/review
app/api/v1/alerts.py             ← /api/v1/alerts
app/api/v1/selfcheck.py          ← /api/v1/self-check + /status
app/core/health.py               ← _model_status / _capture_status / _db_status（健康检查纯逻辑）
app/middleware/upload_limit.py   ← 自查上传体限制中间件（83 行）
```

**注意**：`/api/v1/self-check` 是**小程序已在用的**接口，路径与响应形状必须**逐字不变**
（`miniprogram/src/utils/selfcheck.ts` 的 `sanitizeSelfCheckResult` 依赖它）。

#### B-3. 事务边界下沉到服务层

**统一范式**（照 `services/scoring/ledger.py` 已有做法）：

```python
# 服务层方法内部管事务，路由层只调服务
class SomeService:
    def do_write(self, ...) -> Result:
        try:
            ...写操作...
            self.session.commit()
            return result
        except Exception:
            self.session.rollback()
            raise
```

**收益**：
- 路由层只剩「参数校验 → 调服务 → 包络」
- 事务语义集中，可统一审计写入
- 消除 9 处重复模板

**范围**：`api/v1/identity.py`(3) + `api/v1/appeals.py`(3) + `api/v1/decisions.py`(3)

#### B-4. 路由层去 SQL

`api/v1/appeals.py` 的 `list_appeals` 直接写 `select(Appeal)` → 下沉到 `repositories/appeal.py`
（`list_by_student` 已存在但被绕过了）。

同时**删除死代码** `statement_rows = ...; _ = statement_rows`。

#### B-5. 后端门禁加固

| 项 | 变更 |
|---|---|
| 覆盖率门槛 | `fail_under` 60 → **85** |

| 新增 CI 步骤 | `python -m pytest --cov=app --cov-report=xml` 后跑 `scripts/check_layering.py` |
| layering 检查脚本 | `scripts/check_layering.py`：断言 `domain/` 不 import `sqlalchemy`/`services`/`repositories`；断言 `api/` 不出现 `session.execute`/`select(` |

## 第四部分：实施纪律

### 4.1 批次门禁

| 批次 | 门禁 |
|---|---|
| A | `ruff + mypy strict + pytest`（新增 15 例）+ **真浏览器验证登录→dashboard** |
| B | `ruff + mypy strict + pytest` **零改动既有测试**（行为等价证明）+ 覆盖率不降 |
| C | `vue-tsc + eslint --max-warnings 0 + build` + `check-design-tokens` 通过 + **视觉回归截图对比** |
| D | 各子项自带门禁 |

### 4.2 批次 B/C 的额外要求（重构专属）

1. **零行为变更** —— 不改接口路径、不改响应字段名、不改状态码
2. **既有测试必须全绿且不允许修改既有断言** —— 唯一允许的是补测试
3. **一次只拆一个文件** —— 拆完跑门禁，再拆下一个
4. **用 `git diff` 逐个确认** —— 不看 diff 不接受

### 4.3 严禁事项（防屎山）

| 禁止 | 理由 |
|---|---|
| ❌ 一次性大重构 | 无法审查、无法回滚 |
| ❌ 引入新 UI 库 | 依赖膨胀；Element Plus + 自研组件已够 |
| ❌ 路由层再出现 `session.execute` | layering 检查脚本会红 |
| ❌ domain 层 import 任何 I/O | 纯度是决策引擎可单测的前提 |
| ❌ 保留 `suppress(Exception)` 静默吞异常 | 静默失败是最贵的 bug |
| ❌ 前端 `any` / 硬编码色值 / 魔法间距 | 令牌铁律 |
| ❌ 组件 `<style>` > 100 行 / 单文件 > 400 行 | 拆分门禁 |
| ❌ `TODO` / `pass` 桩 / 注释掉的代码 | 半成品是代码质量杀手 |
